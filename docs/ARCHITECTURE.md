# Architecture

Curio keeps a single catalog and immutable original store. Tags and collections organize the same media rather than moving files between physical libraries. Normal and hidden modes differ only in query scope, so both modes share every browsing and editing feature.

## Collection and Visibility

An asset is identified by the SHA-256 of its uploaded bytes. The catalog records the original name, editable title and notes, source URL, author, media properties, star, trash state and processing progress. Many-to-many memberships associate an asset with tags and collections. Global byte-identical deduplication reuses the asset and preserves new source observations without changing its existing manual hidden flag.

Organization status is derived from memberships: an asset with at least one tag, collection or enabled game-screenshot classification is organized. Live assets with none belong to the scoped inbox. Details, inbox filters and inbox counts use the same predicate, including hidden containers and screenshots with an unassigned game. Removing the last organization source returns an asset to the inbox. Titles, notes and stars do not affect this status. The legacy database column is retained but neither read nor written; this predicate change requires no catalog rewrite.

Effective hiding is the logical OR of an asset's own flag, any associated hidden tag and any associated hidden collection. Membership inheritance is computed at query time instead of being copied into the asset flag. Removing one hidden source reveals an asset only when no other hidden source remains. Asset details expose those sources as hidden reasons.

Normal scope contains only effectively non-hidden assets; hidden scope contains only effectively hidden assets. Lists, keyword search, inbox, stars, trash, jobs, membership counts and collection covers use the same scope predicate. Non-hidden containers can mix both kinds of assets and display the corresponding subset in each mode. A hidden container never appears in normal container choices.

The browser stores the selected mode only in memory. New loads and reloads start in normal mode; in-application navigation retains the mode. Two non-repeated consecutive `q` key presses within 1.5 seconds toggle it globally, including text fields. Composition and Ctrl/Command/Alt combinations do not count, and the shortcut does not swallow normal text input. Holding the sidebar Curio brand for 800 ms also toggles the mode with touch, pen or mouse; on mobile, open the navigation drawer first. A short press retains home navigation. Movement over 10 px, pointer cancellation or window blur cancels a pending hold; completed holds and drags suppress the following pointer click. The brand disables native image dragging, selection and touch callouts. Both entry points share the same mode switch, which invalidates old view state and selection. Uploaded originals and known media URLs keep the ordinary shared device-authentication contract; hidden mode adds no access-control layer.

Browser navigation uses `/curio/collections/<id>` for a collection, `/curio/tags/<id>` for a tag, `/curio/` for all media and `/curio/<view>` for other sidebar sections. A page load restores the selected section or container from the path; in-application navigation updates browser history without reloading. Opening a preview pushes one history entry, switching media replaces it, and Back closes the preview without resetting gallery filters or position. Forward can reopen a still-loaded item in the same visibility scope. Search, filters, selections, preview data and hidden mode remain in memory. Switching mode clears the active container and replaces the current URL with its section path.

In media views, Ctrl/Command+A enters selection mode and selects the complete current filter result, including unloaded pages, up to the API's 2000-item batch maximum. Repeating the shortcut retains the selection; the toolbar button toggles select-all. Text fields retain native text selection, and dialogs and previews take precedence over gallery shortcuts. Escape closes the active overlay first; otherwise it cancels pending select-all requests and exits selection mode.

In the media viewer, A/Left Arrow and D/Right Arrow navigate to the previous and next media without wrapping at the ends. Text input, composition, Ctrl/Command/Alt combinations, handled key events and the metadata editor retain their own behavior.

Media cards show their tags, omitting the currently open tag. Within a tag or collection, they also annotate other collection memberships, omitting the currently open collection. Dragging a sidebar tag onto an individual card adds that membership without replacing existing tags. Mouse drags activate after six CSS pixels; touch drags require a 450 ms hold. Moving over ten pixels before that hold cancels the gesture and preserves ordinary vertical scrolling. Dragging a card or viewer tag at least 64 CSS pixels from the starting pointer position turns its floating label red; releasing removes only that membership. Returning within the threshold, Escape, pointer cancellation or navigation cancels removal. A membership chip also opens a readable action menu with explicit removal and cancellation. Successful quick changes offer an eight-second undo using the saved asset's effective scope. These gestures and menus do not open previews or change gallery selection. The selection toolbar can remove only the current membership from selected media through the existing incremental batch edit. Original bytes, other memberships and manual flags remain unchanged; removing the last hidden membership can move an asset into normal scope according to effective hiding.

Collections can be deleted from the collection grid or their management dialog after confirmation. Deletion removes the collection, its memberships and internal groups while retaining all assets and their other memberships. An asset returns to the inbox only when no organization source remains; removing its last hidden source restores normal visibility.

Quick tag edits update loaded cards and viewer details from the saved asset response, then synchronize scoped sidebar counts. They do not enter page loading state; unaffected gallery and image nodes stay mounted. Visibility, inbox, tag-filter or search changes reconcile the matching gallery in place, including totals, pagination and group members. Unaffected cards, selection and expanded groups remain intact; responses from a previous view are ignored.

Tag and collection index searches filter the current index rather than switching to All Materials. Metadata and batch organization share searchable tag/collection choices with inline creation. Creating a container preserves selected media and draft choices; applying organization remains one atomic asset patch. Dirty editors guard backdrop, Escape, close and cancel actions, and pending saves disable dismissal. Failed gallery thumbnails retry in place through refresh, an explicit retry action or connectivity restoration. Mobile editing and action controls use larger targets and readable labels without changing the established visual language.

### Collection Groups

Collections support unnamed groups of media. A media item belongs to at most one group within each collection and can be grouped independently in other collections. Creating a group ignores selected media already grouped in that collection and requires at least two remaining distinct items. The toolbar disables creation when fewer than two ungrouped items are selected. Adding selected items to an existing group moves only their grouping in that collection. Removing items from a group or dissolving a group keeps the media in the collection. Groups have no separate visibility flag or effect on organization status.

Group membership is stored in additive catalog tables with foreign keys to both the group and the asset's collection membership. Removing that collection membership or permanently deleting an asset removes its corresponding group link. Replacing a membership set preserves links for retained collections. Trash changes only asset state, so restoring an asset restores its group placement. Opening an existing catalog creates the new tables without rewriting existing tables or media.

The same scope, search and filter predicates select group members, preview covers and counts. A mixed-visibility group appears with its matching subset in each mode; filtering down to one item retains the group. Collection pagination counts each group once, anchored by its first matching member in the selected sort order. Before revealing a collection, the browser fetches all matching grouped media in bounded ID batches and loads and decodes their safe thumbnails. Only ordinary media and gallery-entry pagination remain lazy. Select-all still selects matching media rather than group anchors.

New page loads and newly created groups start collapsed. Expansion state stays in memory through SPA navigation. Group edits synchronize gallery entries and prepared members in place without a loading screen or remounting the gallery. Creation briefly coalesces up to six visible thumbnails into the new stack while surrounding cards settle into their new positions.

Collapsed groups use stacked safe thumbnails. Collections pack visible cards using untransformed dimensions instead of browser column fragmentation. The next card uses the leftmost column whose bottom is within one gallery gap of the shortest column, so small aspect-ratio differences do not scatter nearly level rows; larger height differences favor shorter columns. Expanded members pack together in adjacent columns from a shared top edge, using no more columns than the group has members. Their occupied columns resume below the group's tallest column, preventing unrelated cards from filling gaps between its members; columns outside a smaller group remain available to ordinary cards. Group cards retain their slightly smaller width, subtle individual edge accents and group marks instead of an enclosing panel.

Clicking the stack expands the group; clicking an expanded member's group mark or caption folds it. Media previews, selection and group actions retain their own clicks. Group thumbnails are never lazy-loaded, including while folded. Folding retains loaded card and image nodes, hides them without reserving gallery space and stops hover animation playback. Even the first expansion only switches visibility and performs no member or thumbnail loading. Short CSS motion keeps every opened image visible while the cards settle; document-wide snapshots and stagger delays are not used. Reduced-motion preferences minimize these effects.

Refreshes and filters within the same media view retain gallery and image nodes, including collection groups, with a brief opacity change and progress on the refresh control. Pending or failed result updates suspend gallery actions; failures keep the previous content with an error and retry entry. Changing mode, section, tag or collection requires new scoped data before presenting a gallery, so old-scope results are not shown under the new selection. Follow the shared [refresh diagnosis](https://github.com/Crashmere/agent-config/blob/main/skills/server-operations/references/common-issues.md#a-data-refresh-flashes-or-resets-the-page).

## Game Screenshots

The product section remains named "游戏截图" and accepts static images and game recordings. Both use the same assets, original store, media gallery, viewer and batch editing as other media; recordings retain the ordinary native/compatibility video player. A separate game registry gives each game a stable identity and an optional unique Steam App ID. Names are editable display metadata: naming a Steam ID applies to its current media and future imports. Games from other platforms can be created by name and associated manually; tags and collections remain independent.

Browser routes are `/curio/games` for the game index, `/curio/games/<id>` for one game, `/curio/screenshots` for all game media and `/curio/games/unassigned` for game media without an assigned game. Deep links restore the same shared gallery; ordinary scope-reset and SPA mode-retention rules still apply. Escape closes overlays or exits selection first, then returns an open game folder to the game index without reloading.

Uploads inside the game index or screenshot gallery explicitly enter this section. PNG/JPEG and supported video filenames matching `<positive-app-id>_<YYYYMMDDHHmmss>_<digits>.<extension>` supply a game identity and capture time. An existing Steam ID reuses its game; a new ID creates a game. The complete date must be valid and the App ID must fit an unsigned 32-bit integer. The final numeric component is accepted without assigning it a meaning. Names without a recognized game identity enter the unassigned game, independently of capture-time recognition. Uploading inside a specific game supplies an explicit game target without changing time inference. File selection, external drops and clipboard uploads share this target, and queued uploads retain it through navigation and retries.

Uploads outside these views do not infer screenshot classification from a filename. Ordinary uploads without tags or collections enter the inbox, where the organization dialog can move selected images and recordings into game screenshots through the shared classification editor. Automatic classification recognizes original and recorded source names for newly enabled members; explicit game assignment can instead choose a named game or leave it unassigned. Game screenshot members are excluded from the All Materials view and its count, including keyword search and filters within that view. Explicit tag/collection views, stars and trash continue to include their matching game media.

New or explicitly re-enabled screenshot members take capture time from a valid Steam filename first, including recorded source names for existing assets. Otherwise, filename recognition accepts a complete fourteen-digit `YYYYMMDDHHmmss` token preceded by `_` and followed by `_` or the end of the filename stem, before the extension. The full date and time must be valid. It checks names in their existing order and takes the first valid token from the first matching name; this generic recognition supplies time only, not a game identity. If no filename supplies a valid time, the existing ExifTool runtime reads the immutable original's embedded capture, creation and modification timestamps and chooses the earliest valid recorded wall-clock value. These include EXIF/XMP `DateTimeOriginal`, `CreateDate` and `ModifyDate`, PNG creation/modification times and media/track creation/modification dates. Comparing creation and modification avoids treating a later copy or export date as the capture date when an earlier embedded timestamp survives. Metadata reads are bounded to fifteen seconds and occur before the catalog write transaction. Missing, invalid or unreadable metadata leaves time unknown. Server filesystem dates and collection time are not capture-time fallbacks; an upload does not retain the source device's filesystem dates. This rule performs no startup backfill over existing classifications.

Capture time is stored separately from collection time as a timezone-free local timestamp with second precision. Recorded wall-clock values are retained, including when embedded metadata carries an offset; no server/browser timezone conversion is performed. Screenshot browsing defaults to capture time descending, supports ascending order and puts unknown times last in either direction. Its grid reads left to right before starting the next row, preserving visual chronology instead of column-first packing. Single-item editing can correct or clear the time; game assignment preserves each already enabled item's capture time and infers time for newly enabled members.

Screenshot metadata records a manual opt-out as well as active membership. Reimporting identical bytes preserves existing screenshot metadata, including manual game/time corrections and opt-outs, regardless of upload origin. Explicit organization can re-enable an opted-out asset. Automatic classification of already enabled members leaves their metadata unchanged. Removing screenshot classification returns an asset to All Materials and, if no tags or collections remain, to the inbox. Other source observations still accumulate under the existing deduplication contract.

The game list, counts, latest capture time and covers use the asset's common effective-visibility predicate and exclude trash. Game folders are ordered by their latest known capture time descending, with unknown-time and empty folders last. Equal times retain case-insensitive name or Steam App ID ordering, then game ID. A game with live screenshots only in another scope is omitted. Empty games appear in their creation scope so they can be selected before an upload. Game identity and name are shared across modes; game assignment itself adds no hiding inheritance.

Confirmed game deletion uses the same availability predicate as the game list. One transaction clears every reference to that shared identity, including hidden and trashed media, then removes the game entry. Detachment preserves capture times and screenshot classification, so live images and recordings return to unassigned game media rather than All Materials or the inbox. Original bytes, visibility and other memberships remain unchanged. New Steam uploads can recreate the deleted identity's game; existing assets retain their manual unassignment on duplicate import.

Initial activation on a legacy catalog creates additive `games`, `screenshots` and `catalog_features` tables and performs one transactional image-filename recognition pass. The completion marker and screenshot rows commit together without updating asset rows, memberships or uploaded bytes. Completed catalogs retain their existing game classifications; adding video support and the new upload/organization rules introduces no second backfill or data rewrite. Older programs can ignore the added tables; original-byte identity remains unchanged.

## Durable Uploads

Dropping external files inside a tag or collection captures the current scope and container at drop time, before any asynchronous folder traversal. Each queue entry retains that target through navigation and retries. Queue deduplication includes scope and memberships, so a file already queued for one container can also be imported into another. Upload preparation adds the requested memberships to exact duplicates without replacing their existing memberships or manual hidden flag.

The browser uses at most two file lanes, each with an independent cancellation controller and a hash worker reused for that batch. Each file is hashed incrementally before preparing a session with its SHA-256 and expected size. Files with the same hash serialize preparation and transfer so a later duplicate can reuse the first committed original. Different files can upload concurrently; each file sends its chunks in order, bounded by the advertised server maximum of 128 MiB. Per-file pause, retry and queue removal do not resume unrelated files. Removing a queue row preserves acknowledged server bytes; clearing finished rows applies only to the panel's presentation scope. Retained sessions resume with their own destinations and expected hash, independently of the page currently open.

Each chunk includes its intended offset; the server serializes work per hash and reports the authoritative durable offset after flushing accepted bytes. Sent-byte events animate the browser's progress bar but never advance its resume offset. An interrupted or uncertain request is recovered by reading server status and resuming from that offset. Pause cancels both lanes, including hashing, status requests and retry delays; resume reacquires authoritative offsets. The browser shows a separate complete-file verification phase and reaches 100 percent only after the server confirms publication. Workers are terminated when a batch stops. Upload-triggered gallery refreshes are coalesced to once per second and flushed at batch completion; the unfinished-upload list refreshes on panel opening and batch lifecycle changes.

Final completion checks the entire uploaded size and server-computed SHA-256 before publishing the immutable original and catalog entry. Upload acceptance is separate from preview readiness: the original can be stored while a durable media task is still queued or running. Preparation detects global exact duplicates; it does not silently move an existing asset between visibility modes. Queue rows explain retained destinations, effective hiding and existing trash state, and explicitly open the stored asset without restoring it. Successful completion reports actual effective hiding while the queue retains its initiating presentation scope; the original upload scope still determines only a new asset's own hidden default.

Confirmed incomplete-upload discard first stops browser transfers for that hash and persists server cleanup intent under its transfer lock. Older same-byte queue entries are canceled even when their hashes finish later; newly selected files remain eligible. Cleanup removes only the selected partial/session and any uncataloged interrupted-publication object, retaining cataloged originals and repair metadata. Failed cleanup stays visible as `discarding` and resumes through the existing worker, without a schema migration or separate timer. Processing status polling uses the same bounded 60-ID batches as grouped-media preparation, preventing large gallery selections from becoming oversized query strings.

New assets default to the upload scope's hidden flag. Original objects live under hash prefixes, incoming files retain acknowledged partial content, and preview derivatives use separate paths. Total original size is independent of the per-request chunk ceiling.

The shared `nas`, `ali` and `vps` Nginx servers retain the existing 4 MiB HTTP/2 receive window. Curio's location disables request buffering and allows a 129 MiB request body. The window, chunk maximum and request deadline control different stages; none is a configured throughput cap. Large home imports should use the direct NAS LAN entrance.

## Media Processing

Durable asset status drives a bounded background queue. NAS runs two processing jobs and permits one Curio GPU operation at a time, below ordinary service priority. CPU media operations share a two-slot budget, with one slot reserved from background processing for online playback. Metadata extraction, native decoding, resizing and encoding write only Curio derivatives and work files. Worker failure records an error for retry rather than invalidating the accepted original; interrupted processing is requeued on restart.

Still-image previews preserve transparency. Animated GIF, WebP and APNG retain original animation for playback while the gallery uses a still thumbnail. SVGs use safe raster previews rendered at the thumbnail and viewer sizes while retaining their original logical dimensions; originals are downloads rather than executable inline documents. ICO decoding selects one frame before the ordinary image pipeline, avoiding repeated generic decoder delegation. Video imports generate metadata and a thumbnail, not a complete playback MP4; video readiness does not depend on an online cache.

On `nas`, JPEG processing uses Curio's embedded worker with the existing pinned NVIDIA image runtime selected by `CURIO_IMAGE_PYTHON`. Video processing probes FFmpeg CUDA/NVENC support, with software-decoded GPU and full CPU fallbacks. Transparent, animated, vector and fidelity-sensitive image paths retain explicit CPU fallbacks. Originals are never recompressed or rewritten by preview generation.

### Image Viewing

Images open fitted to the available canvas. Raster images are not enlarged on initial display; safe SVG raster previews can fill the canvas. The zoom percentage maps one original pixel to one CSS pixel at 100 percent, independently of the initial fit. Wheel zoom follows the cursor, and touch pinch follows the moving midpoint; panning is bounded to keep image edges from leaving empty space on an overflowing axis. Double taps enlarge from fit and restore fit when zoomed. Images at least 2.5 times as tall as wide enlarge to the canvas width when whole-image fit leaves horizontal space, and expose a width-fit toolbar action. The toolbar also provides separate actual-size and whole-image fit controls. Fit follows canvas resizing; changing media resets the transform.

Mobile and coarse-pointer viewers fill the viewport in both orientations, with floating controls and an initially closed bottom details panel. At fit size, horizontal touch swipes switch media and downward swipes close the viewer; enlarged images pan instead, including vertical reading of long images. Double taps zoom around the tapped point without also toggling controls. Pinch release and cancellation cannot become navigation. Loading feedback stays outside the transformed image. A thumbnail remains visible while the clear preview loads or after a loading failure; a successful preview removes that underlay so transparent media retains its alpha. Preview failures offer an in-place retry, and connectivity restoration retries a failed preview once without resetting zoom or pan. The next loaded still preview can warm after a short dwell, except when offline, backgrounded, using Save-Data or on a reported 2G connection. Ordinary galleries load the next catalog page near the viewer boundary.

Browser-supported still formats load their immutable original on enlargement or when the preview lacks enough pixels for the display's pixel density. Automatic original loading waits 240 ms and is limited to 32 MiB and 40 million pixels; larger images offer an explicit load action. The existing preview stays visible until original decoding completes, and replacement preserves size and position. Leaving the image cancels its loader. Failed or unsupported original decoding retains the generated preview; SVGs always retain safe raster previews and never load their original into the viewer. Animated images below 30 MiB start with their original playback resource; larger animations wait for explicit play. Pause captures the displayed frame and unmounts the animated image to stop decoding, retaining zoom and background selection. Play and Replay restart the animation; backgrounding pauses it. Viewing changes neither original bytes nor stored derivatives.

Clipboard actions distinguish the generated preview from a PNG at original raster dimensions. Original copying requires browser-decodable still media within 32 MiB and 40 million pixels, preserves alpha, and does not modify stored bytes. Preview copying also bounds decoded pixels to 40 million; SVG uses only the safe generated preview. Leaving the asset cancels pending copying.

### Tank Revealing

The image viewer offers a local-only tank revealing dialog for browser-decodable static raster originals. Prism mode expands an inclusive luminance range into full RGB levels, fills cover pixels and adjusts contrast. Traditional mirage modes composite alpha over exact black or white. The same viewer retains zoom and pan while comparing the original with a decoded result.

Opening the dialog analyzes the original once in the existing browser worker. PNG `tEXt` and JPEG EXIF `Make` presets from Prism take precedence and supply the thresholds and contrast. Without a preset, at most 16,384 spatially distributed, jittered sample locations and their original-resolution neighbors guide a bounded dark/bright band search. Samples are not interpolated or resized: the search checks luminance separation, recurring masks across neighboring cover pixels, spatial coverage, decoded color coherence and clipping. Strong, unambiguous band evidence initializes Prism thresholds, modest contrast and neighborhood-fill iterations; other plausible bands remain selectable. These are heuristic recommendations, not a guaranteed reconstruction of the encoding parameters or the user's intended image.

Uncertain results retain the original until the user selects a candidate or changes a parameter. Transparent images offer black/white composites without claiming that ordinary transparency proves a mirage tank; opaque images offer dark/bright Prism trials. Manual edits never rerun analysis or get overwritten by a later recommendation. Restoring a strong recommendation reuses the initial analysis; uncertain cases retain the manual 0-24 default reset. No analysis result is stored in the catalog or sent to another service.

Pixel processing runs in one browser worker, using WebGL2 where available. Prism neighborhood filling uses the upstream weighted iterative GPU algorithm; its CPU fallback averages already-decoded left/top pixels, as in the upstream fallback, without iterations. Directional copy fills use CPU. Thresholds and filling operate on original-resolution pixels. Their result is cached independently of contrast, so contrast changes reuse the existing revealed texture or CPU buffer instead of repeating the neighborhood passes.

Slider input submits parameters on animation frames without waiting for a pause or pointer release. One decode runs at a time, with pending changes coalesced to the latest parameters. GPU previews apply contrast in a display shader and transfer an `ImageBitmap` with a longest edge of at most 1280 pixels, avoiding full-image pixel readback. CPU previews resize already-revealed pixels and apply contrast to the bounded buffer. Resizing encoded originals would mix the hidden luminance levels, so downsizing occurs only after revealing. Completed frames draw into the existing canvas with the original image's logical dimensions; intermediate results remain useful while newer parameters are pending, and an older frame cannot replace a newer one. The UI identifies these as quick previews; their resized contrast clipping can differ from a downscaled full-resolution export.

Downloading requests original-resolution output at the selected parameters and encodes a separate PNG. Parameter controls remain disabled during that explicit export. Failures retain the last rendered image and disable result downloads until a current result succeeds. Closing the dialog cancels loading, terminates the worker and releases bitmaps and object URLs.

Revealing reads the unchanged authenticated original, never a resized preview or a third-party service. It accepts at most 64 MiB and 16 million decoded pixels, with browser codec support required; animated and SVG assets are excluded. A downloaded full-resolution PNG is a separate local output, not a catalog mutation. Originals, stored derivatives, metadata and memberships stay unchanged. The adapted algorithms and their MIT notice are recorded in [Third-Party Notices](THIRD_PARTY_NOTICES.md), which is included in the browser build and downloadable from the dialog.

### On-Demand Video Playback

Each newly opened video starts muted in both viewers; users can enable sound through the playback controls. The desktop viewer retains native controls, autoplay and posters, reveals application controls on mouse movement, and exposes the manual compatibility action above the video. Mobile and coarse-pointer viewers prepare the descriptor without autoplay, expose a large explicit play action, and use 44-pixel play/pause, mute, speed and fullscreen controls. Progress can seek before initial playback. Preparing, buffering and failure have distinct feedback; controls hide after 2.6 seconds of idle playback and return on interaction or pause. Native Safari fullscreen remains a fallback when element fullscreen fails. A manual compatibility action handles playable but unsuitable originals while preserving the viewed position and speed.

Both viewers select suitable MP4/MOV and WebM originals through a capability descriptor. Native eligibility includes full-range 8-bit H.264 and H.264/HEVC with PCM16 audio, while retaining the near-zero source-timestamp requirement. The browser tries an original when its codec hint or container MIME is supported; incomplete hints alone do not force transcoding. An actual playback failure, or metadata with no video dimensions, switches to HLS. Start timestamps outside the 1 ms native tolerance retain a normalized compatibility timeline. Supported transparent WebM uses its original; detected alpha streams are not flattened into opaque H.264 when native playback is unavailable. [API](API.md#media-and-downloads) defines native eligibility.

Compatibility playback uses a finite HLS playlist and request-triggered four-second H.264/AAC MPEG-TS segments. Native HLS browsers use their own pipeline; other supported browsers lazily load hls.js. A distant seek requests the target neighborhood rather than encoding all preceding footage; native HLS may request opening segments to discover metadata. Source orientation is applied to decoded pixels and source frame rates are retained. GPU-supported stages prefer CUDA/NVENC; software decoding and color normalization use bounded CPU fallbacks.

HDR compatibility output is BT.709 limited-range SDR. A bounded source-frame probe uses valid MaxCLL, falling back to mastering-display maximum luminance, before linearization removes that metadata. The explicit tone-map peak uses units of 100 nits, with fallback values of 100 for PQ and 10 for HLG. After full-resolution linearization, decoded frames are downsized to at most 1920 pixels per dimension before CPU float Mobius tone mapping; even dimensions and sample-aspect-ratio adjustment retain display proportions without enlarging smaller videos. This generic SDR conversion does not apply Dolby Vision RPU dynamic adjustments. Native playback can retain HDR on a capable browser and device instead. Shared diagnosis is documented in [Video playback and HDR tone mapping](https://github.com/Crashmere/agent-config/blob/main/skills/server-operations/references/common-issues.md#unnecessary-video-transcoding-and-hdr-tone-mapping).

Identical fragment requests share a cancellable job. Two generators and eight total queued/running playback jobs share a 256 MiB cache/reservation limit, with an 8 MiB segment output bound and a 75-second generation deadline. Idle entries expire after twenty minutes or are evicted under cache pressure. Pausing and leaving stop unnecessary MSE requests; native HLS controls its own look-ahead. Selected permanent deletion cancels, drains and evicts its playback work before unlinking; shutdown drains jobs before closing the catalog. NAS scratch uses private tmpfs under `/run/curio/playback`, separate from stored derivatives and recovery material.

## Deletion and Recovery

Moving to trash changes catalog state and is reversible. Permanent deletion accepts only explicitly confirmed selected trash assets. It persists cleanup intent before canceling selected processing and removing their live original, derivatives, work and catalog relationships. Interrupted cleanup resumes from that intent; unrelated assets and existing backups are not changed.

Recovery requires the complete independent catalog, originals, stored derivatives, durable partial uploads and work state. The server-operations full external workflow captures that state through Curio's Portal resource declaration. Downloadable runtimes remain reconstructable program dependencies outside the data recovery scope. Program rollback changes the executable, not the catalog or deleted media.
